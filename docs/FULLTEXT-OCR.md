# 全文 OCR：方案、质量与边界

> 版本 v0.1 · 2026-10-25
>
> 目标不是"把扫描件转成文字"，是**在 1638 页里能按关键词找到那一页**。
> 这两件事的精度要求差一个数量级。

## 为什么需要它

原厂手册是纯扫描件，**1638 页全部零文字层**（逐页实测 `get_text()` 返回 0 字符）。
没有全文索引，用户想查"气门间隙多少"只能凭记忆翻。

## 方案：Windows 内置 OCR

用 `Windows.Media.Ocr`（系统自带，含简体中文模型），不用第三方大包。

| 优点 | 代价 |
|---|---|
| 零下载，装好系统就有 | 只支持 Windows 10/11 |
| 200–750ms/页 | 密集小字页错字率高 |
| 中文识别够定位用 | 表格数字不可靠 |

**为什么不选 PaddleOCR / RapidOCR**：都要下几百 MB 模型，实测装包反复超时；
而定位用途上 Windows OCR 已经够。真要换引擎，接口不用改——`ocr.py` 只依赖
`ocr_win.ps1` 这一个黑盒，换实现即可。

## 实测数据（200dpi，A4）

| 页面类型 | 速度 | 质量 | 结论 |
|---|---|---|---|
| 症状表 / 故障表 | 750ms | **好**（"制动总泵（主缸）活塞不正确返回"全对） | 直接用 |
| 规格表格 | 700ms | 中等（数字常错） | 只定位，数字看原页 |
| 密集小字正文 | 1000ms | **差**（"通风良好"→"通风蚜"） | 只定位 |
| 目录页 | 800ms | 差（密集小字+特殊符号） | 检索用不上 |

### DPI 对比（同一页密集正文）

| DPI | 字符数 | 质量 | 结论 |
|---|---|---|---|
| 200 | 875 | 差 | **选它** |
| 300 | 899 | 差（略好一点点） | 更慢，不值得 |
| 400 | 851 | 更差 | 过采样有害 |

**结论：200dpi 就够了。** 200 → 300 的字符数只差 24 个，肉眼可辨的错误率几乎一样。

### 图像增强：反而有害（重要）

试过 `enhance.py` 的白场拉伸 + 锐化组合（三种参数）：

| 参数 | 字符数 | 结果 |
|---|---|---|
| 白场60 对比1.6 锐化150 | 836 | 比原图更差 |
| 白场90 对比2.0 锐化180 | **513** | **崩溃，几乎不可读** |
| 白场45 对比1.3 锐化120 | 874 | 与无增强持平 |

**原因**：锐化会强化笔画边缘的锯齿，OCR 的连通域分析被干扰。
增强对"人眼看图"有效（所以 `pages/` 那批增强图值得），对 OCR 无效。

**这条经验省掉了一次全量重跑。**

## 边界（写死在 SKILL.md 里）

**OCR 文本只用于定位页码，绝不用作数据来源。**

- 搜到"气门间隙 0.15"→ 去看原页确认是 0.15 还是 0.75
- 任何扭矩、间隙、电压值，必须看原页
- 网站搜索结果页和 Skill 输出里都带这条提示

理由：`M10` 会被识别成 `MIO`，`0.15` 可能变成 `0.75`。
**一个错的扭矩值能让发动机报废，而 OCR 的错误看起来和正确的一样可信。**

## 管道结构

```
builder/ocr.py             主线：渲染 → 调 PowerShell → 清理 → 写索引
builder/ocr_win.ps1        Windows OCR 封装（纯 ASCII，路径走 job.json）
builder/ocr_sources.py     建立 索引文件名 → PDF 绝对路径 的映射
        ↓
pack/data/ocr/<doc_id>.json     每页 {doc, file, page, text, chars}
pack/data/ocr/_sources.json     原 PDF 路径（本机配置）
pack/data/ocr/pagecache/        按需渲染的原页缓存
        ↓
web/server.py  /api/fulltext   只搜全文
               /api/search     合并搜（含 manual 结果）
               /api/manualpage 按需渲染原页 PNG
```

### 为什么路径走 job.json 不走命令行参数

PowerShell 5.1 接收含中文的命令行参数会乱码（实测过，路径变问号）。
所以 Python 把路径写进 `%TEMP%\wa_ocr_job.json`，ps1 从文件读。
**任何含中文路径的 ps1 调用都应该这么做。**

### 为什么 ps1 里不能有中文注释

PowerShell 5.1 读无 BOM 的 .ps1 时按 ANSI(GBK) 解码，UTF-8 中文变乱码。
注释行虽然被忽略，但乱码可能产生意外字符。`ocr_win.ps1` 全文件纯 ASCII。

## 中文清理规则

Windows OCR 的原始输出每个汉字之间插空格（`注 意 事 项`）。

`clean_text()` 的处理顺序：

1. 汉字之间的空格去掉，**反复跑到不变**（`注 意 事 项` 要跑 3 遍才干净）
2. 汉字与全角标点之间的空格
3. 括号内侧空格
4. 折叠多空格、多空行
5. **英文/数字之间的空格保留**（`MTR 10A` 不能被合并成 `MTR10A`）

## 怎么重跑

```bash
PY=python          # 确保 python 在 PATH；不在则写绝对路径

# 试跑 10 页
"$PY" builder/ocr.py --src "<手册目录>" --pack packs/x --doc-id x --limit 10

# 全量（断点续跑）
"$PY" builder/ocr.py --src "<手册目录>" --pack packs/x --doc-id x --skip-existing

# 登记原 PDF 路径（让"看原页"能用）
"$PY" builder/ocr_sources.py --src "<手册目录>" --pack packs/x --doc-id x

# 质量分级（必须跑，否则搜索结果没有 quality 字段）
"$PY" builder/ocr_quality.py --pack packs/x
```

OCR 是 CPU 活，1423 页实测 **18 分 45 秒**（0.79s/页）。可以后台跑，不影响写拓扑。

## 质量分级（2026-10-25 实测）

SX4 两个文档合并后的 1537 页结果：

| 等级 | 页数 | 占比 | 含义 |
|---|---|---|---|
| `good` | **1326** | **86.3%** | 可疑字 <8%，文字可信 |
| `sparse` | 125 | 8.1% | 字太少，多半是插图页 |
| `fair` | 76 | 4.9% | 8–20%，看原页为准 |
| `poor` | 8 | 0.5% | >20%，基本不可用 |
| `empty` | 2 | 0.1% | 纯图 |

拆开看：

| 文档 | 页数 | good 占比 | 备注 |
|---|---|---|---|
| `sx4-2007`（维修手册正文） | 1423 | 90.1% | 纯文字页，识别最好 |
| `sx4-2010`（电路图） | 114 | 低一些（大量 sparse/fair） | 电路图本身字少，且编号密集 |

**电路图页的 `sparse` 不是问题**——那类页本来就是图，文字只有连接器号和线色，`sparse` 恰恰是正确的分级。

打分方法：该页汉字中"全库出现次数 ≤5 的罕见字"占比。
不依赖外部字表，也不需要人工词典——正常行文里不会出现罕见字，出现多半是识别错。

### 踩过的坑：`_` 开头的文件不是索引

`data/ocr/` 下同时存在 `sx4-2007.json`、`sx4-2010.json`（页面索引）和
`_sources.json`、`_quality_report.json`（辅助文件）。
加载时必须跳过 `_` 前缀，否则会把辅助文件的结构当成页面数据，报
`AttributeError: 'list' object has no attribute 'get'`。

## 检索的实际能力边界（重要，别过度承诺）

**搜术语：行。搜数字：不行。**

实测（SX4 手册 1537 页）：

| 查询 | 命中页数 | 结论 |
|---|---|---|
| `制动警告灯` | 10 | ✅ 准 |
| `安全气囊` | 30 | ✅ |
| `轮速传感器` | 8 | ✅ |
| `正时链条` | 8 | ✅ |
| **`E323`（连接器号）** | **28** | ✅ **这是最值钱的用法** |
| `G144` | 8 | ✅ 且同时命中 5 个结构化系统 |
| `气门间隙` | **0** | ⚠ 手册里没有这个说法（可能写作"气门挺杆间隙"） |
| `0.15` / `0.25` | **0** | ❌ **数字几乎搜不到** |

**为什么连接器号特别好用**：电路图上连接器编号是独立的大字标注，OCR 识别得准。
搜 `E323` 能同时拿到：结构化拓扑里哪个系统用它 + 原图哪一页画着它 + 连接器布置图里它在车上哪个位置。

**为什么数字搜不到**：OCR 会把 `0.15` 识别成 `015`、`0 15`、`O.15` 等形式，
小数点和小字号数字极不稳定。所以"查某个扭矩值是多少"这件事，靠全文检索做不到。

**正确的用法**：

```
搜术语（气门 / 制动 / 轮速）→ 定位到几页 → 点开原页 → 人眼读数字
```

这也是为什么 `/api/manualpage` 按需渲染原页不是可选项，而是配套必需。

**如果用户搜的词没命中**，可能是手册用了别的说法，不是系统坏了。
提示语应该引导："试试更短的词，如「气门」而不是「气门间隙」"。
