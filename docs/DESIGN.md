# WrenchAtlas 设计文档

> 版本 v0.2 · 2026-10-24 · 状态：设计已确认，可进入 M1
> 项目路径：本文档用 `<项目根>` 指代你 clone 下来的目录

---

## 1. 一句话定位

**把原厂维修手册（扫描件）变成可检索、可点选、可推理的车型知识图谱，用两个前端交付：给人看的网站，给 AI 用的 Skill。**

首款车型：长安铃木 SX4（2010，1.8L M18A）。架构从第一天就按多车型设计。

---

## 2. 三条不可动摇的设计约束

这三条决定了后面所有技术选择，改动任何一条都要重做架构，所以放在最前面。

### C1 · 引擎与车型数据分离

代码里**不允许出现任何车型专属的字面量**（"天语"、`E323`、`M18A`、某个页码）。

- 引擎只认**数据包（Vehicle Pack）**
- 增加一款车 = 新增一个数据包目录，**一行代码不改**
- 这是"以后能做别的车"的唯一保障。任何为了赶进度把车型数据写进代码的决定，都是技术债的起点

### C2 · 一个数据层，两个前端

| 前端 | 服务对象 | 核心动作 |
|---|---|---|
| **Web 网站** | 人（你） | 看图、追线、看动画、查规格 |
| **Skill** | AI（我） | 检索定位、诊断推理、给页码溯源 |

两者**共享同一份车型数据包**，不各自维护副本。任何数据只在一个地方定义，两边只做投影。

这一条的直接收益：你在网站上验证过的数据，Skill 立刻就能用；Skill 发现的错误，改一处两边都修好。

### C3 · 原图永不入库（版权红线）

原厂手册扫描件受版权保护。开源仓库里**绝不能出现**：

- ❌ 手册 PDF 原件
- ❌ 从 PDF 渲染出的页面图片（PNG/JPG）
- ❌ 大段原文转录

**可以入库的**只有结构化事实：连接器编号、针脚归属、回路拓扑、诊断步骤编号与判据、规格数值、以及"某事实位于某文档第几页"的锚点坐标。

这个边界同时解决了三个问题：开源合法、仓库体积可控、多车型免于法律风险。

**推论**：必须提供一个 `builder` 工具链，让任何人拿**自己合法持有的手册**跑出**自己的数据包**。这才是开源的正确形态——开源的是方法和引擎，不是内容。

## 3. 架构

```
                    ┌──────────────────────────┐
   原厂手册 PDF ───► │  builder  （数据生产，离线）│
   （你自己持有）     │  渲染 / 分色 / OCR / 标注  │
                    └────────────┬─────────────┘
                                 │ 产出
                    ┌────────────▼─────────────┐
                    │   Vehicle Pack（数据包）    │
                    │   JSON · 车型无关格式       │
                    └──────┬─────────────┬──────┘
                           │             │
                  ┌────────▼───┐   ┌─────▼────────┐
                  │  web 网站   │   │  skill       │
                  │  人看       │   │  AI 用       │
                  └────────────┘   └──────────────┘
                           │             │
                    原图页图片        同一份 JSON
                    （本地，不入库）
```

关键点：**pack 是唯一事实源（SSOT）**。builder 生产它，web 和 skill 消费它。原图在本地独立存放，pack 里只留指针。

## 4. 数据模型

四类实体。全部 JSON，文件名即语义，不引入数据库依赖（可选用 SQLite 做索引加速）。

### 4.1 Page · 页面锚点

一切溯源的终点。回答"这个结论在哪一页"。

```json
{
  "id": "sx4-2010::wiring-10::p1",
  "doc": "2010年长安天语SX4 电路图/06-系统电路图/10-挡风玻璃雨刮器和清洗器.pdf",
  "page": 1,
  "title": "挡风玻璃雨刮器和清洗器线路图",
  "kind": "wiring",
  "system": "wiper",
  "image": "pages/wiring-10-p1.png",
  "size": [4560, 3613]
}
```

- `kind` 枚举：`manual`（正文）/ `wiring`(线路图) / `connector`(连接器布置) / `harness`(线束) / `ground`(接地点)
- `image` 指向本地渲染图，**该目录已 gitignore**
- 页码锚点必须能定位到"文档 + 页"，而不是手册里的印刷页码（扫描件印刷页码不可靠）

### 4.2 Circuit · 电路拓扑

用连接器针脚做节点，这是本项目最核心的数据结构。

```json
{
  "id": "wiper-main",
  "system": "wiper",
  "name": "前雨刮主回路",
  "source_page": "sx4-2010::wiring-10::p1",
  "nodes": [
    { "id": "E323.9", "connector": "E323", "pin": "9", "role": "source",
      "bbox": [1520, 240, 1680, 300] },
    { "id": "E64.3",  "connector": "E64",  "pin": "3", "role": "load",
      "bbox": [1120, 1620, 1260, 1680] }
  ],
  "wires": [
    { "from": "E323.9", "to": "E64.3", "color": "L", "gauge": "0.85",
      "verified": false }
  ],
  "grounds": ["G334"],
  "confidence": "read-from-scan-unverified"
}
```

- `color` 用铃木线色代号（B 黑 / W 白 / R 红 / L 蓝 / Y 黄 / G 绿…），取值表放 `pack/colors.json`
- `bbox` 是该针脚在原图上的像素框，网站用来画热区
- **`verified` 与 `confidence` 是硬字段**，不是可选装饰。未经人工核对的拓扑必须能被前端标红——这是防"看起来对但会误导排查"的机制

### 4.3 Diag · 诊断

这是 Skill 的主食。

```json
{
  "id": "dtc-p0301",
  "type": "dtc",
  "code": "P0301",
  "title": "1 缸失火",
  "system": "engine",
  "possible_causes": ["点火线圈", "火花塞", "喷油器", "压缩不良", "线束"],
  "steps": [
    { "no": 1, "action": "读取失火计数，确认是否单缸",
      "check": "仅 1 缸计数上升",
      "yes": 2, "no": 8,
      "ref": "sx4-2007::manual-11::p23" }
  ],
  "related_circuits": ["ign-coil-1"],
  "spec_refs": ["spark-plug-gap"],
  "source_page": "sx4-2007::manual-11::p21"
}
```

- `type` 枚举：`dtc`（故障码）/ `symptom`（症状问诊表）/ `procedure`（拆装）
- `steps` 是决策树，`yes`/`no` 指向下一步序号，`null` 表示终点
- 症状表（手册里的"症状诊断表"）是最高价值素材，天然就是决策树

### 4.4 Spec · 规格

```json
{
  "id": "spark-plug-gap",
  "item": "火花塞间隙",
  "value": "1.0–1.1",
  "unit": "mm",
  "condition": "M18A 发动机",
  "engine": "M18A",
  "source_page": "sx4-2007::manual-01a::p42",
  "applies_to": ["sx4-2007", "sx4-2010"]
}
```

- `engine` 与 `applies_to` 是**必需字段**——这正是 1.8 与 1.6 混用风险的防线
- 规格类数据必须可点回原页核对，网站要提供"看原文"一键

### 4.5 规格来源守卫（M18A 专属，但机制通用）

已确认车辆为 **M18A（1.8）**，而这套资料里维修手册正文是 **2007 版，对应 M16A（1.6）**。这是本项目最大的数据污染源：M18A 是 M16A 的扩缸衍生，大量零件通用，但**扭矩、间隙、标定相关参数未必相同**。

因此规格数据强制双字段：

```json
{
  "id": "spark-plug-gap",
  "engine": "M18A",
  "source_engine": "M16A",
  "engine_mismatch": true,
  "value": "1.0-1.1",
  "source_page": "sx4-2007::manual-01a::p42"
}
```

| 字段 | 含义 | 谁填 |
|---|---|---|
| `engine` | 该规格**适用**的发动机 | 人工判定 |
| `source_engine` | 该数值**抄自**哪本手册对应的发动机 | 从手册归属推导 |
| `engine_mismatch` | 二者不一致时置 `true` | 自动计算 |

**前端强制规则**：

- `engine_mismatch: true` 的规格，数值旁必须显示醒目警示："数值摘自 M16A 手册，你的车是 M18A，请以实车/4S 数据核对"
- 电路类数据同样适用：2010 版电路图未标注排量，ECM 针脚定义可能与 1.8 实车有差，凡涉及 ECM 针脚的条目一律 `verified: false`，直到你实车核对过

**这不是过度谨慎。** 照错的扭矩拧缸盖螺栓，是能直接把发动机报废的。宁可每条都提醒，也不能让一个数字悄悄溜过去。

## 6. 技术选型与理由

| 层 | 选型 | 理由 |
|---|---|---|
| 网站 | **原生 HTML/JS + FastAPI**（v0.3 修正，原定 Next.js） | 单页类应用，SSR/SEO 无价值。去掉 npm 与构建步骤：双击 bat 即用、手机零配置、开源门槛更低（只需 Python） |
| 数据 | JSON 文件 + 可选 SQLite 索引 | 数据量不大（千级回路、万级连线），JSON 让开源者能直接看懂、手改、diff |
| 电路图渲染 | 原图 PNG 作底 + SVG 矢量层叠加 | 原图不改（保持原厂权威性），交互全在叠加层，符合 C3 |
| 图形处理 | PyMuPDF + numpy + OpenCV | 已验证：PyMuPDF 2.0 已装，分色实验跑通 |
| OCR | RapidOCR（本地 onnx） | 零成本、离线、可反复重跑；仅用于建索引，不承担识别精度责任 |
| Skill | WorkBuddy Skill + 本地脚本检索 | 不让 AI 把 1638 页塞进 context，改为脚本按需取 |

**不选数据库的原因**：开源者 clone 下来要能直接跑。JSON + 一个 `pack.json` 比要求他们装 PostgreSQL 友好一百倍。等真的卡性能了再加索引层。

## 7. 关键取舍记录

| 决策 | 选择 | 放弃了什么 |
|---|---|---|
| 重绘策略 | 原图打底 + 矢量交互层 | 放弃"全量重绘成漂亮矢量图"。理由：重画不会比原厂准，且丢失原厂权威性 |
| 动画范围 | 按回路建模，不做全量 | 放弃"114 页全动"。理由：无正确拓扑的动画会误导排查，比不动更有害 |
| OCR 定位 | 只做索引，不做权威文本 | 放弃"OCR 出全文知识库"。理由：扫描件 OCR 必然有错字，扭矩/间隙错一位就出事 |
| 数据格式 | JSON 平文件 | 放弃关系数据库的查询能力 |
| 开源内容 | 引擎 + builder + 格式规范 | **放弃"连数据一起开源"**。理由：版权红线 |

## 9. 安全边界

- 所有结论必须能一键跳回原页核对，**不允许出现无溯源的断言**
- `verified: false` 的拓扑在前端显式标红
- 涉及安全气囊、制动、转向的诊断，网站上固定显示"以原厂手册为准，本工具仅辅助定位"提示
- 不提供扭矩/间隙的"推算值"，只提供手册原文值 + 页码

## 10. 交付形态与部署边界

### 10.1 一个必须先说清的矛盾

你说"网站可以部署就行"，但这里和 C3 版权红线直接冲突：

**网站要显示原厂手册原图。一旦部署到公网服务器，就等于把原厂手册内容公开发布。**

所以边界定死：

| 场景 | 是否可行 | 说明 |
|---|---|---|
| 本机 `localhost` | ✅ | 原图随便看 |
| **家里局域网（手机 WiFi）** | ✅ | 手机直接访问，这是你要的"手机上看" |
| 公网部署 | ❌ | 会公开传播原厂手册，违法风险 |
| 出差在外要看 | ⚠️ 后续可选 | 用 Tailscale / ZeroTier 组虚拟局域网回家，**不开公网端口** |

**结论：不做公网部署。** 你要的手机访问，家里 WiFi 就够了，比公网还快还安全。

### 10.2 启动方式

```
双击 start.bat
  → 检查依赖
  → next start --hostname 0.0.0.0 --port 3000
  → 控制台打印本机 + 内网访问地址 + 终端二维码
  → 手机扫一下直接进
```

bat 要做的事：自动探测内网 IP、打印 `http://192.168.x.x:3000`、生成终端二维码。你连 IP 都不用记。

### 10.3 手机端设计要求（M1 就要考虑，不能事后补）

| 项 | 要求 |
|---|---|
| 布局 | 响应式，手机上单列，电路图占满宽度 |
| 触控目标 | 针脚热区最小 44×44px，**点按触发，不依赖 hover** |
| 画布操作 | 双指缩放 + 单指拖动；双击复位 |
| 电路图 | 手机默认横屏提示；竖屏时提供"旋转查看"按钮 |
| 溯源跳转 | 点页码后在手机上是新标签打开 PDF 对应页（或站内看图） |

**关键**：原图 4560×6135 像素，手机上直接全图显示等于啥也看不清。必须有"总览 → 放大局部"两态，而不是一张缩小的图。

## 11. 开源协议

### 11.1 定案

| 部分 | 协议 | 文件 |
|---|---|---|
| 代码（`core` / `builder` / `web` / `skill`） | **MIT** | `LICENSE` |
| 车型数据包（`packs/*/data/` 下产出的结构化数据） | **CC BY-NC-SA 4.0** | `LICENSE-DATA` |
| 文档（`docs/`） | **CC BY 4.0** | `LICENSE-DOCS` |

### 11.2 为什么这么配

**代码用 MIT**——你要的是"对我有用、别人也能用"。MIT 是最不折腾的协议：一行字，谁都能用、能改、能商用。CC 那套对代码反而添乱。你的收益是传播，不是收授权费。

**数据包用 CC BY-NC-SA 4.0**——这是保护你的劳动：

- `BY` 署名：别人用了得标你名字
- `NC` 非商业：**防止别人拿你逐页校验出来的数据去做付费产品**。这是你最该防的
- `SA` 相同方式共享：防止有人拿你的数据套个壳闭源发出去

**NC 不会绑住你自己。** 你是版权人，将来想商业化（比如做个付费版），可以给自己另发商业授权，NC 只约束别人。

### 11.3 一个法律上的细节

数据包里**不含原图**，只含"连接器编号—针脚—回路"这类结构化事实。这类汇编结构受著作权保护的程度低于原文，用 CC 协议明确授权，比留白更安全，也省得别人来问你"能不能用"。

### 11.4 仓库必须有的免责

必须在 README 顶部和网站每个页面底部出现：

> 本工具不包含、不分发任何原厂维修手册内容。使用者需自行合法持有对应车型手册。维修操作请以原厂手册与专业判断为准，因误用造成的损失作者不承担责任。

## 12. 图的三种表达（候选方案 · 待确认）

### 12.1 核心判断：诊断要的不是接线图，是信号流图

原厂电路图是**接线图**——画的是精确到每根线、每个针脚位置、线色代号，用途是拆装和量针脚。

而诊断时需要的是一张**功能信号流图**：电源 → 保险丝 → 开关 → 继电器 → 负载 → 搭铁，5–10 个框，一眼看出哪一环断了。

这两张图服务两种完全不同的场景，不该用同一张。

| | 接线图（原厂） | 诊断信号流图（本项目重绘） |
|---|---|---|
| 内容 | 全部针脚、连接器、线色、走向 | 功能环节与信号流向，省略旁枝 |
| 用途 | 拆装、找线、量电压 | 判断故障在哪一环 |
| 手机 | 4560px 宽，需缩放探索 | 竖屏一屏看完 |
| 动画 | 像素图，做不到 | 有拓扑即可算电流路径 |
| 版权 | 原厂，仅本地 | **本项目原创表达** |

### 12.2 三层结构

| 层 | 形态 | 给谁 | 能否入库 |
|---|---|---|---|
| **接线图** | 原厂扫描页 | 看细节、量针脚 | ❌ 仅本地 |
| **诊断信号流图** | 本项目重绘的 SVG | 诊断判断 | ✅ 原创，可开源 |
| **拓扑数据** | JSON 节点与边 | AI 推理、动画驱动 | ✅ 原创，可开源 |

三者的关系：信号流图的每个框都可点击 → 跳到接线图对应位置看细节。**精度留给原图，清晰留给重绘，推理留给数据。**

### 12.3 为什么不是"重绘全部接线图"

- 全量重绘 114 页接线图，要还原全部细节，且还原结果不会比原厂更准确
- 重绘目标是"看起来像原图"，这是最费力且价值最低的方向
- 提炼 37 张信号流图，首批三系统只需 10–15 张，工作量差一个数量级

### 12.4 法律依据（简要）

- **功能性事实**（连接器编号、针脚归属、谁连谁）不受著作权保护，属于思想/事实范畴
- 受保护的是**表达**：原图的具体绘制、手册的原文文字
- 用标准电气符号重新绘制的功能框图，是独立创作的新表达，与原图不构成实质相似
- 本地个人使用原图不涉及传播，无风险；**分界线在"公开"这一步**

### 12.5 对 M1 的影响

若采纳本方案，M1 的做法从「原图打底 + 手标 bbox 热区」改为「重绘 SVG + 节点即元素」：

- 省掉手工标注像素坐标的全部工作（节点本身就是 SVG 元素，无需 bbox）
- 天然可缩放、清晰、手机友好
- 但需要在 `circuits` 数据里增加布局字段（节点的画布坐标与样式）

**待确认**：是否采纳"诊断信号流图"作为 M1 主交付形态，原厂图退居为"看细节"的二级页。

## 13. 图像处理的边界（硬约束）

### 13.1 一句话

**保真型处理可以用，生成型 AI 一律禁用。**

### 13.2 为什么生成式 AI 不能碰电路图

即梦、Midjourney、Stable Diffusion、豆包图像生成——这类模型的训练目标是"**产出看起来合理的图**"，不是"**精确复制输入的图**"。它们的本质是**推测缺失像素**，而推测就会出错，且出错不可控、不可检测。

在电路图上，这意味着：

| AI 的"合理推测" | 实际后果 |
|---|---|
| 把 `E323` 补成 `E328` | 你去车上找 E328，找不到 |
| 把 `8` 画成 `3` 或 `6` | 引脚号错，量错针脚 |
| 把两条平行的线"优化"成一条 | 回路凭空少一条 |
| 把 `G334` 的搭铁点挪个位置 | 你按图找搭铁，找错地方 |
| 把模糊的线色 `L`（蓝）认成 `W`（白） | 追线追到另一条路 |

**关键问题不是"它可能出错"，而是"你无法知道它哪里出了错"。** 生成式模型不留修改痕迹，你看不出哪一笔是被"补"出来的。

对一份用来判断"发动机为什么不着火"的资料，这是不可接受的。**看着清楚但内容是编的，比模糊但真实危险一万倍。**

### 13.3 可用的工具（保真型）

| 类型 | 代表 | 作用 | 会改内容吗 |
|---|---|---|---|
| 文档超分辨率 | Real-ESRGAN（文档模型）、SwinIR | 放大去噪 | ❌ 只做像素插值，不增删线条 |
| 二值化/去噪 | OpenCV、PIL | 提升对比度、去 JPEG 伪影 | ❌ |
| 矢量化 | Potrace、Vectorizer.AI、Illustrator Image Trace | 位图转矢量 | ❌ 拓扑保持 |
| OCR / 版面分析 | PaddleOCR、DocTR、LayoutLM | 提取文字与位置 | ❌ 只读数不生成 |
| 视觉理解 | 多模态模型读图 | 回答"这条线连到哪" | ❌ 只读不改 |

### 13.4 这些本地就能跑，不必交给豆包

- **隐私**：手册虽公开，但没有上传的必要
- **可控**：参数可调、可 A/B 对比、可复现
- **成本**：零
- **批量**：114 页一次跑完

唯一值得调用外部强模型的地方是**"读图理解"**（帮我判断拓扑），而不是"改图"。

### 13.5 最重要的一条：如果全做完还看不清，问题不在图

先把话说在前面。L0 增强 + L1 追线 + L2 重绘都做完仍然觉得看不清，通常不是图像质量问题，而是**信息量问题**——一张图上几十条线，人脑本来就不该同时处理。

**正解不是把整张图变清楚，而是把"必须看的部分"缩到最小。**

诊断时你只需要看一节：确认是"电机没电"之后，才需要看那一段线。所以真正的目标链条是：

```
缩小范围（诊断流图给出该查哪一环）
   → 只看那一小块（局部放大 + 点亮）
      → 到这一步才需要"看清细节"
```

### 13.6 兜底策略：换源，不要硬猜

如果某几页扫描质量确实低于可用阈值（字都断了、线都糊成一片），**正确做法是换一份更清晰的资料源**，而不是让 AI 去补。

- 该车型可能有其他版本/其他渠道的电子手册
- 花钱买正版电子版，比花时间修图便宜
- 单页坏了就单页换，不必整套重做

**在烂图上死磕是性价比最差的选择。**

### 13.7 判定标准

一页图是否"够用"，用这三条判：

1. 所有连接器编号能**无歧义**读出（E323 不会看成 E328）
2. 所有引脚数字能**无歧义**读出
3. 线色代号能**无歧义**辨认

三条任一不满足，该页进"待换源"清单，不进知识库。**宁可标"此页不可用"，也不标一个可能是错的结论。**

## 14. 验证机制（重要变更 · 2026-10-24）

### 14.1 前提变了

原设计把 `verified` 定义为"实车核对过"。**但老莫不能拆车，这条路径实际不可用。**

必须改为**不依赖实车**的多级置信度。

### 14.2 三级置信度

| 级别 | 含义 | 判定依据 | 前端表现 |
|---|---|---|---|
| `read-clear` | 原图清晰可读，判读确定 | 编号、引脚、线色三条判定标准全过 | 正常显示 |
| `read-uncertain` | 原图模糊或接法复杂，存疑 | 有任一项判读不确定 | **黄色角标 + 悬停显示存疑原因** |
| `vehicle-confirmed` | 实车核对过 | 万用表实测/拆解确认 | 绿色角标 |

**已淘汰**：`verified: true/false` 的二元布尔。它无法表达"读得清楚但没实车验"这个最常见的中间状态——而这恰恰是当前 100% 数据的状态。

### 14.3 交叉印证（替代实车核对的主要手段）

在不能拆车的前提下，可信度靠**多源比对**建立：

1. **2007 版 × 2010 版** 同一系统对照，两版一致则可把置信度提到 `read-clear`
2. **同图内自洽**：连接器编号在"连接器布置图"里能查到对应位置和针脚数
3. **功能自洽**：拓扑是否符合该系统的电气常识（如起动机必须有电磁开关和搭铁）
4. **真值表校验**：如雨刮开关档位表，可与实际档位行为对照

### 14.4 必须诚实的地方

- **所有当前数据都是 `read-clear` 或 `read-uncertain`，没有一条是 `vehicle-confirmed`**
- 前端和文档都不得暗示"已验证"
- 存疑项必须逐条列出，不能藏在正文里

**这不是保守，这是唯一诚实的做法。** 用户拿这份数据去修车，他有权利知道哪一条是"我读的"、哪一条是"量过的"。

## 15. 平台化落地（2026-10-25）

第 2 节写了「增加一款车 = 新增一个数据包，一行代码不改」。**那是设计意图，这一天才真正做到。**
以下是实际暴露出来的隐藏假设，以及各自的处理。

### 15.1 审计结果：五处只认 SX4

| 位置 | 隐藏假设 | 后果 | 处理 |
|---|---|---|---|
| `builder/index.py` 的 `SYSTEM_SLUG` | 中文标题→slug 的映射写在工具里 | 换车型必须改 builder 源码 | 外置到 `packs/<id>/system-map.json`，工具只读它 |
| `web/server.py` 的 `CONF["pack"]` | 单值，全程假设只有一个车型 | 两个车型包无法共存 | 拆成 `packs` / `default` / `pages` / `conn`，全部按 id 索引 |
| 所有 API | 无 `pack` 参数 | 前端无法指定查哪款车 | 全部接口加 `?pack=<id>`，缺省用默认包 |
| 前端 `index.html` | 硬编码「长安铃木 SX4 · M18A」 | 换车型界面显示错 | 从 `/api/pack` 动态取 |
| `skill/query.py` | 默认路径写死 `suzuki-sx4-2010` | 问别的车会去搜 SX4 的数据 | 扫描 `packs/`，加 `--list-packs` / `--pack` |

### 15.2 新增的三件基础设施

**① 系统标识词表（`docs/SYSTEM-TAXONOMY.md`）**

不同厂牌对同一功能叫法不同（"充电系"/"充电系统"/"发电机"），统一成 `charging` 以后才能跨车型对照。
词表分动力/底盘/灯光/车身/空调/网络六类，60+ 标识，并规定新增标识必须登记——否则平台化断在这里。

**② 数据包脚手架（`builder/new_pack.py`）**

一条命令生成完整可跑骨架（7 个文件 + 5 个目录 + README 填写指南）。
不是复制空壳——生成的 `pack.json` / `system-map.json` 都带 TODO 注释和格式示例。

**③ 车型上下文（`web/static/packbar.js`）**

解决"手机点来点去不想每次带参数"：URL `?pack=` > localStorage > 服务端默认。
单车型包时切换器自动隐藏，不干扰。

### 15.3 两个设计决策

**默认车型包按数据完整度选，不按字母序。**

第一版实现用字典第一项，结果演示包 `demo-*` 排在 `suzuki-*` 前面，成了默认。
正确做法：`pack.json` 里 `"default": true` 的最优先，否则比 `data/circuits/` 里的系统数量。
**排序规则不能依赖目录名字**，那是巧合不是设计。

**`_` 开头的目录不参与运行时。**

`packs/_template` 有 `pack.json`，被扫描逻辑当成真车型，还抢了默认位。
约定：`_` 前缀 = 模板/示例，`discover_packs` 直接跳过。

### 15.4 双包验证记录（已删）

造了一个假包 `demo-car-2020`（2 页图 + 1 个系统）实测：

| 项 | 结果 |
|---|---|
| 服务同时加载 2 个包 | ✅ |
| circuits / pages 按包隔离 | ✅ 23 vs 1，互不串 |
| `?pack=` 切包后 `source_label` / `source_image` | ✅ 指向本包 |
| 图片按包取 `/media/pages/xxx?pack=` | ✅ |
| 报告按包生成 | ✅ |
| 默认包选择 | ✅（修了上面的 bug 后） |
| 坏 pack id | ✅ 404 |

验证完删除该包——里面是从 SX4 复制的页图，不能留在仓库。

### 15.5 还没做到的
